Software 10x Slower: Root Cause Is Serial Dependencies in Architecture, Not Code

Software that is 10 to 100 times slower than necessary is rarely a code-trick problem; it's a serial dependency chain set at the architecture stage. The right optimization is to lock the hardware's theoretical peak and measure the gap—provided the architecture decision-makers understand assembly.

Performance neglect is an incentive problem, not a technical one

Casey argues that developers generally don't care about performance, and the mechanism has three layers: in enterprise software, users aren't the buyers—decision-makers only look at cost, compliance, and legal liability, so performance doesn't affect deals. Monopoly effects make platforms like social networks hard to challenge on performance; users can't leave even if the experience is bad. The third reason is that people who've been calling for performance over the past decade have had an effect, and performance is starting to be valued again. These three layers explain why 'making software faster' often has no voice in companies, and they show that performance is fundamentally an incentive problem.

22:29

Profile-then-optimize is not how experts do it

Casey stresses that true optimization experts in the industry don't profile first and then fix hotspots. The correct order is: first ask what operations the system must perform, then check what the underlying hardware can do at its theoretical peak, then measure the gap between the theoretical maximum and the current implementation, and finally work to close that gap. This has two benefits: you won't be misled by local hotspots, and you'll discover new hardware features, thereby improving your own optimization skills. He explicitly says that 'measure hotspots first, then optimize' is not the expert approach—it treats optimization as an afterthought.

— Casey Muratori
32:53

Serial dependency chains set the performance ceiling at architecture time

The real problem with 'premature optimization is the root of all evil' is that if a serial dependency chain forms during the architecture phase, later hotspot optimization can't save it. Casey gives an example: if the code pattern is 'request-process-request-again', even performance experts are helpless because serial dependencies can't be parallelized. Software performance is usually determined by the longest serial dependency chain, and that chain is set during architecture. So once an architecture choice is wrong, all subsequent performance optimization is building on a faulty foundation.

40:04

AI companies are paying off the language debt of the previous generation

Uber once moved from Python and Node.js to Go and Java due to single-threaded issues. Now OpenAI and Anthropic face the same story: data scientists are familiar with Python, so initial versions are all in Python, but products need to support multithreading and more connections, so they're now evaluating migrations to Rust or Go. Casey's subtext is that AI companies are going through an infrastructure 'language debt' period, and this scene has already played out in the previous generation of internet companies—history is repeating.

GTA6 is slow because it must replace the company's cash cow

Casey explains from a business structure perspective why GTA6's development cycle is so long: GTA5 Online was the highest-grossing entertainment product at the time, earning billions of dollars annually. GTA6 isn't making a new game; it's replacing the company's most profitable product, so Rockstar and Take-Two can't fail, and they have to plan the online component to avoid the new product cannibalizing the old one's revenue. GTA5's success was an accident for them; GTA6 is the first real update of a flagship product, equivalent to re-releasing Google Search—this is an extremely conservative development logic.

1:19:40

The real cost of virtual functions is that compilers dare not optimize

Many think the virtual function call itself is expensive, but Casey corrects that: the real cost is the compiler losing optimization ability. When the compiler can't determine the runtime type, it can't inline, merge redundant code, or vectorize, and the performance loss is far greater than one indirect call. The degradation he showed in the Clean Code video is relatively mild; real production environments can be worse. Polymorphic code is slow not because of that one dispatch, but because all the surrounding code loses its eligibility for automation.

Glossary

theoretical peak
The maximum throughput hardware can achieve under ideal conditions; the benchmark for optimization targets.
serial dependency chain
A sequence of operations that cannot be parallelized and must execute in order, setting the lower bound on software latency.
hotspot
The part of a program that consumes the most CPU time; often the natural entry point for optimization.
branch prediction
A CPU mechanism that predicts the direction of branches to keep the pipeline full; mispredictions are costly.
