The hardest unsafe Rust: safety must survive deliberately incorrect user code

The unsafe code in IDDQD must guarantee memory safety even against deliberately broken user code: comparison functions can lie, thread-local variables can be corrupted, but Rust's safety rules cannot break.

IDDQD avoids duplicating keys by borrowing them from records

When Oxide stores CockroachDB records indexed by UUID, Rust's built-in map requires keys and values separated. This forces a choice: either duplicate the key in every value (error-prone) or pass tuples everywhere (awkward). IDDQD lets users store complete records and specify how to extract the key. Early versions used cloning (safe Rust), but composite keys that cannot be cloned forced Rain to develop an unsafe solution: borrowing keys directly from records rather than copying them.

Unsafe Rust isn't disabling safety—it's acknowledging compiler limits

Rain invokes Rice's theorem—equivalent to the halting problem—which proves no algorithm can perfectly determine if arbitrary code has undefined behavior. Rust's compiler chooses stricter than perfect: it rejects some actually-safe programs to guarantee that safe Rust never accepts one with undefined behavior. Unsafe is the escape hatch for code programmers know is safe but compilers cannot verify, transferring responsibility from machine to human.

— Rain Paharia

The hardest unsafe: when correctness depends on untrusted user code

IDDQD's unsafe code depends on user-implemented traits: hash functions, comparisons, others. Users can break the contract—comparison functions can flip results randomly, identical keys can hash to different values each time. This requires an ‘infosec mindset’ rather than a ‘software engineering mindset’: treat user code as a potential attacker. Core principle: user code may be broken and produce bugs, but it cannot break Rust's underlying memory-safety guarantees.

— Rain Paharia
58:40

Bun's rewrite from Zig to Rust raised the bar for unsafe discipline

Rain discovered a real bug in IDDQD while watching Bun's translation project: a million lines of Zig translated to Rust in nine days using AI, with the project already having stopped accepting pull requests. He didn't oppose translation itself, but the resulting unsafe code scattered throughout the codebase didn't meet his standard for ‘responsible unsafe Rust’—code that users relying on safe Rust can trust. This motivated him to write out what ‘responsible unsafe Rust’ actually demands.

— Rain Paharia

Mutable iterators escape their scope by design, relying on human promises

Before Rust 1.0, the design decision was: values returned by iterators could escape the for loop and be collected into a vector, potentially creating multiple simultaneous mutable references to map elements. The compiler cannot prove these references are non-overlapping, so iter_mut uses unsafe to ‘guarantee’ the compiler that each yielded value is distinct. If buggy user code tricks IDDQD into storing duplicate indices, that guarantee fails—two mutable references point to the same memory.

— Rain Paharia
1:11:50

Detect failed user code, drop to safe linear scan

Rain found he could write an Ord implementation that mostly returns correct results but strategically returns wrong ones, tricking IDDQD into storing duplicate indices. The fix has two parts: first, use a tiebreaker to ensure no incorrect matches; second, once user code is detected as untrustworthy, remove operations degrade from efficient index lookup to a full linear scan that never calls user code. This trades performance for a guarantee: even broken user code cannot cause undefined behavior.

— Rain Paharia
1:24:30

Claude Opus 4.7 and GPT-5.5 found real bugs as adversarial testers

Rain took pathological test cases and seeded them into Claude Opus 4.7 and GPT-5.5, asking them to break IDDQD's invariants. After roughly twenty minutes of reasoning, GPT-5.5 found a genuinely invariant-breaking method; Claude Opus 4.7 and it each independently discovered one or two other cases. This works well because results are immediately verifiable with Miri—unlike speculative reasoning where correctness is hard to judge.

— Rain Paharia
1:30:10

IDDQD sits on the boundary between Miri's two verification models

Miri is a tool that interprets Rust's intermediate representation (MIR) to detect whether unsafe code violates aliasing rules. It provides two models: stacked borrows, the older, accepted, but overly-strict model; and tree borrows, an attempt to be more permissive. IDDQD must pass both in CI. Rain needed to write specific workarounds just to satisfy stacked borrows—evidence that this library sits precisely on the fault line between where the two models diverge.

— Rain Paharia

Glossary

Rice's theorem
Any non-trivial semantic property of programs is undecidable; a generalization of the halting problem.
Miri
A tool that interprets Rust's intermediate representation (MIR) to detect if unsafe code violates aliasing or memory rules.
stacked borrows / tree borrows
Two competing formal models in Miri for determining whether mutable reference aliasing is valid.
panic safety
The property that a data structure remains consistent even if user code panics (unwinds) during execution.
