Agent memory isn't a chat log, it's an information retrieval system

LLMs are stateless, and you can't make them remember by stretching the chat history. Long-term memory has to live outside the session: MEM0 uses three stores, extracts every turn, and at retrieval time weights vectors, keywords and entities separately, pulling back only the few dozen most relevant entries.

Agent architectureLong-term memoryVector retrievalMEM0
It takes apart MEM0's three layers — storage, ingestion, retrieval: how the three stores divide the work, what extraction and recall each do, and how the 2.5-point formula is computed. All architecture detail you can copy directly, not a concepts lecture.

The argument · tap a timestamp to hear it

1:04

Long-term memory is not a stretched chat log

An LLM is itself a stateless machine; nothing persists between two consecutive prompts. An ordinary agent's ‘memory’ is just resending the entire conversation history with every new request — that's conversational memory; the moment a new session opens, all context resets to zero. Real long-term memory therefore has to be a separate service that survives across sessions, holding user preferences, knowledge the agent has learned, and procedures, and letting the same user share one memory across multiple agents. The test is simple: it cannot live in the same store as the session. This sets the premise for everything that follows: an externalised memory system.

4:07

Entities get their own store, and retrieval gets a shortcut

MEM0's information architecture is a trio. The main store is a vector store holding each ‘memory’ itself (a sentence or a short passage) plus its metadata: creation/update dates, whether it belongs to a user or an agent, a content hash, a lemmatized version, and so on. The second is the entity store, also a vector store, but each point is a person, place or other entity, and the entity's metadata links to one or more main memories — mention Paris and every memory tied to Paris comes along. The third is SQLite, which stores no recollections, only two streams: a log of all change history, and the last 10 messages. The first two stores handle semantic association; SQLite supports short-term context and auditing.

10:12

Memories are extracted by an LLM, not stored wholesale

Ingestion runs after each agent turn, and MEM0's default is infer=true: the turn's messages go to an LLM dedicated to ‘memory extraction’, with the prompt carrying a user summary, relevant old memories and recent messages, and the model emits structured JSON containing the standalone memories to archive. There are two alternatives: procedural mode, which restates the whole operation sequence and which the author considers no longer common, and infer=false, which embeds the messages and writes them straight to the store — too coarse. Extraction is the dividing line between ‘remember the key information’ and ‘keep the full text’.

12:12

Without recent messages, extraction loses its pronouns

The extraction prompt's context is not just the current message. The pipeline first concatenates the turn's messages into a single embedding and searches the main vector store for relevant old memories; at the same time it pulls the last 10 messages from SQLite. That way, when the user says ‘it's great’ or ‘he's good at that’, the LLM can find the antecedent in the preceding sentence or two. Without this module the extraction model loses the reference, and what it extracts is a useless record like ‘it is great’. The prompt also lists the conversation date and the current date. The point: a single message is not enough to be a memory — a memory only holds up inside the recent flow of conversation.

20:18

Retrieval pulls wide first, then reranks down

Retrieval is the same pipeline whether it runs through an explicit agent tool call or automatic injection every turn. The query is embedded and searched against the vector store, but there's a counterintuitive design here: the first pass does not return top K directly. MEM0 first takes max(top_k×4, 60) candidates, then reranks over that coarse pool. The author's example: you want top K=10, and the vector search actually pulls back 60. The reason is that two more scoring passes on different dimensions follow, and if only 10 were retrieved at the start, the reranker would have too small a pool to choose from. By the author's assessment, MEM0 has no query rewriting by default; for better results you should add rewriting yourself on the harness side.

23:20

The fewer entity links, the bigger the retrieval bonus

One of the three scoring passes is entity boost. The system first extracts entities from the query and searches the entity store; each hit entity links to some number of main memories. If only 2 memories were ever bound to that entity, they are probably exactly what you're looking for, and the bonus approaches 0.5; if 1000 are bound, the entity has almost no discriminating power and the bonus approaches 0. In other words, entity boost rewards ‘rare but precise’ clues and penalises broad, catch-all topics. This explains why searching for ‘Paris’ doesn't return encyclopedic Paris trivia but pushes your stored ‘loves the Marais in Paris’ to the front.

24:20

Retrieval ranking can't trust embeddings alone

The final score adds three pieces of evidence for each candidate: vector similarity normalised to 0-1, BM25 keyword lemma overlap normalised to 0-1, and entity boost worth only 0-0.5, for a theoretical maximum of exactly 2.5. That sum is computed for every memory in the coarse pool, then divided by 2.5 to give a final score from 0 to 1, which is used to cut the real top K returned to the agent. The keyword version BM25 consumes was already computed and stored as a lemmatized form at write time, so reranking does no NLP on the fly. The three-way weighting shows MEM0 trusts semantic, keyword and entity signals stacked together by default, rather than betting everything on embeddings.

26:22

Running the whole stack needs no large model

The most underrated thing about this architecture: the most expensive step, ‘memory extraction’, is actually easy — a 1B to 12B parameter model suffices, and anything smaller needs fine-tuning; the author's example recommends Qwen 3 8B. Embedding models can be filtered on Hugging Face by the feature extraction task, then checked against dedicated embedding benchmarks for multilingual or medical sub-leaderboards. If you're in this long term, fine-tune the extraction model on your own scenario. MEM0's embeddings default to a closed model, but every stage can be swapped for local open-source components — which is also why it works as a personal memory foundation.

Glossary

BM25
A sparse keyword retrieval score that rates relevance by term overlap; used alongside vector retrieval for reranking.
query rewriting
Rewriting the user's original question before retrieval so it recalls better; MEM0 does not do this by default.
lemmatized version
Words converted to their dictionary form before being stored, so BM25 can do exact keyword matching.
entity store
A vector store holding the people and place names extracted from memories; each entity carries its linked memories.
