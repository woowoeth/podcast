Why the Soviet GitHub Failed: 30,000 Programs, Only 500 Usable

The Soviet Union established a state algorithmic program library, GosFAP, to solve duplicate software development, but lacked IBM-style hardware compatibility standards and market incentives, ultimately becoming a ‘software graveyard’ filled with useless code.

An obscure but meticulously detailed technical history that explains why standardization, compatibility, and incentive mechanisms matter more than ‘building a repository’; illuminates how open-source collaboration and corporate code reuse work today.

The argument · tap a timestamp to hear it

1:00

IBM's separation of hardware and software created a commercial software industry

In 1964, IBM released the System/360 family, achieving complete software compatibility across models—programs could be ported without modification. In 1969, fearing antitrust litigation, IBM unbundled hardware and software pricing, creating the ‘packaged software’ industry. Users no longer wrote programs themselves or waited for manufacturers to provide them free; they simply purchased them. Within a decade, U.S. packaged software reached annual revenues of $1 billion, funding the country's entire computerization wave.

3:03

Scarce memory forced Soviet programmers to abandon high-level languages

Soviet first- and second-generation computers had memories ranging from 1 word to 32,000 36-bit words—about 144 KB today—while IBM System/360 Model 65 already had 128 KB to 1 MB. Memory was so precious that most Soviet programmers abandoned high-level ‘algorithmic languages’ because compilers consumed too much space; they coded in lower-level autocode or assembly instead. Programs were first handwritten in pencil, then rewritten in ink, then punched twice and cross-checked. Each person got one machine run per day.

9:21

Machines diverged upon installation; software became obsolete with them

Soviet computers left the factory identical, but after installation, vacuum tubes, memory, and I/O components failed and were repaired, gradually making each machine drift from its original model. Since code was written at machine level, bound tightly to the hardware, any change to the machine required rewriting the software. Over time, a single program would become a ‘Frankenstein’ that wouldn't run on any machine in its series. The Tashkent Central Asian Electricity Grid control center, after replacing its computer in 1968, had to rewrite all the software accumulated over five years; a few years later, another model change meant rewriting it all again.

13:28

The state algorithm library was designed as a ‘public library’

In 1968, the Soviet Union formally launched the state algorithm program collection, positioning it like a ‘public library’ or ‘computer users' association’ where software access cost nothing. But this institution, sustained only by donations, was quickly overwhelmed by demand. Meanwhile, sectoral ‘departmental funds’ and regional ‘regional funds’ (such as the Ukrainian Socialist Republic Algorithm Program Fund, which charged access ‘settlement fees’) operated in parallel with almost no coordination.

14:30

Half of ten thousand programs were obsolete or defective

By 1973, Galeev, the director of a computing laboratory in Moscow, wrote in Pravda criticizing the state collection: of over ten thousand algorithmic programs, more than half were considered obsolete or had serious defects. After auditing over two thousand programs used for construction engineering calculations, only 123 were found usable. One Minsk-22 computer's load-bearing frame calculation algorithm had 18 variants, yet none ran correctly. Galeev attributed this to resource scarcity—the state collection, after years of operation, employed only five people, enough only to classify and file newly submitted programs, with no capacity to audit quality.

17:35

The software investment gap was more fatal than the hardware gap

In the 1970s, the Soviet Union standardized its fragmented hardware ecosystem by copying IBM System/360 (Ryad/ES-EVM), and could thereby ‘access’ Western software through conferences, journals, Western software libraries, and in-person exchanges. But this free-rider approach actually starved the domestic software industry of necessary investment. In 1980, the U.S. spent $1 on software for every $1 spent on hardware; the Soviet Union spent only 1.5 to 2 cents per $1 of hardware. At the same time, Moscow State University still had only two BESM-6 computers by 1976, while top U.S. research universities typically had 5 to 15.

19:40

The state library's ‘reuse rate’ was 1/60th of America's

Over a decade after GosFAP's founding, it had catalogued over thirty thousand programs, but only about five hundred were usable—far below the roughly eight thousand high-quality programs available in the U.S. at the time. A member of the Soviet State Committee for Computing Technology and Information Science, interviewed in 1989, noted that American programs had an ‘average reuse rate’ of 100 times, while Soviet programs averaged 1.7 times—indicating that Soviet programmers rarely invested effort to make programs run on machines beyond their own development systems.

20:42

Faced with fragmentation failure, the Soviet answer was always more centralization

Western observers at the time criticized that the Soviet response to centralization failure was always ‘more centralization’: attempts were made to set ‘national standards’ for certain programming languages, even legislating against altering syntax, but standards were chronically delayed and programmers continued working independently. In 1989, that committee member proposed GSPO (‘State Software System’), which would place the entire software chain—development, delivery, maintenance—under direct state control, arguing that GosFAP failed because the state hadn't managed enough. Two years later, the Soviet Union dissolved.

Glossary

System/360
IBM's 1964 computer family that first achieved complete software compatibility across models.
GosFAP
The Soviet Union's central software repository, established in 1975, consolidating programs from regional and sectoral libraries.
ASU (avtomatizirovannie sistemy upravlenniia)
Soviet automated management control systems; the collective term for using computers to assist industrial and economic management.
ES-EVM/Ryad
Soviet standardized computer series from the 1970s modeled after IBM System/360.
