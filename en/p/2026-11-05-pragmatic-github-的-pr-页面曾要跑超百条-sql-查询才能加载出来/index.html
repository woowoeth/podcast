Enterprise edition disguises giant customers as dozens of small teams

Slack's early design sharded data by team; one database per customer. When Enterprise edition launched, to reuse this architecture, the team disguised IBM's separate divisions (marketing, engineering) as independent small teams, created an Enterprise entity to bind them, enabling cross-team DMs and channels. Result: all of IBM's employees querying DMs and large channels hit the same Enterprise shard, which quickly buckled.

17:34

One migration nearly deleted all company Slack messages

To merge three fragmented tables (DMs, public channels, private channels), Maude hand-wrote a thin abstraction layer with dual writes and shadow reads to validate data. After validation passed, she flipped the switch company-wide during all-hands. She discovered data inconsistencies, then deleted the table to re-run backfill—like clearing her local environment—forgetting the switch was company-wide. The sidebar went blank for about 30 minutes; almost no one noticed because everyone was at all-hands.

— Maude
28:47

CEO announcing Friday off triggers a cascade of emoji reactions

CEO posts to the 100k-person channel that everyone gets Friday off. The message broadcasts via WebSocket to all users; in seconds, everyone floods in, pulls history, reacts frantically with emojis. Each emoji reaction broadcasts to everyone else. One message becomes 100k emoji events; 10 emoji types become a million broadcast events. Slack's solution was not architectural—it capped custom emoji reactions at 23 per message. Additional reactions simply don't count.

— Maude
32:57

Multi-role admin receives same message 30 times every time

IBM Slack admin Jeff was simultaneously logged into roughly 30 workspaces. The architecture created one WebSocket connection per workspace; if an Enterprise-level message was visible in all 30 workspaces, his client received 30 identical pushes with no deduplication, often crashing it. This "event flood" only hit power users—exactly Slack's most loyal advocates.

— Maude
41:14

A 500k-connection load test costs $150k just to run once

To validate a 500k-seat customer, Slack initially used Kubernetes to run massive headless Chrome instances simulating real user clicks. Each instance cost roughly $0.37 per 5-hour test; running hundreds of thousands of instances for a complete test burned roughly $150k, with half the time spent restarting crashed Pods. The team abandoned high-fidelity simulation for lightweight Go processes establishing real WebSocket connections and replaying pre-recorded API request sequences, sacrificing some realism for repeatable, low-cost load testing.

— Maude
52:46

Only 16 database shards hold all of GitHub's pull requests and issues

GitHub uses Vitess for MySQL dynamic sharding, but when Maude arrived, all pull request and issue data lived on just 16 shards—far fewer than the thousands-of-shards-per-shard-key pattern she knew from Slack. The culprit was existing scatter queries—lookups without shard keys that must scan every shard to return results. More shards meant slower scatter queries, creating a death lock: to scale, first eliminate scatter queries, but cleanup is far harder than expected.

— Maude
57:51

Five lines of code hide a SQL query worth millions in lost visibility

Rewriting GitHub's Rails code, Maude and colleagues hunted the source of a query on the stars table. They traced it to a five-line function with no visible SQL statement anywhere. She asked her colleague, "Where is the SQL?" The answer: "Mo, that's the million-dollar question." She realized the core trade-off: Slack's Flamework style writes SQL inline; GitHub's ActiveRecord abstracts it away. One is transparent; the other is opaque.

— Maude
59:54

Almost every count on GitHub pages is recalculated in real time

ActiveRecord caches only when query conditions match exactly; any variation requires a fresh database hit. Maude found that GitHub's repository homepage ran over 100 MySQL queries across at least three MySQL clusters, and nearly every displayed count (open PRs, issue count) was live-calculated with no caching. Her take: counts beyond a threshold don't need precision. Display "99+" instead of burning an expensive live query for a number no one cares about.

— Maude

Glossary

Thundering herd
Massive simultaneous client requests for the same resource, overwhelming the system instantly.
Event flood
Client overwhelmed by WebSocket-pushed events in a burst; distinct from thundering herd.
Scatter query
A query without a shard key or primary key, forced to scan every database shard to return results.
Vitess
MySQL sharding middleware enabling more flexible dynamic horizontal partitioning than a single database.
Shadow read
New and old system read in parallel with results compared but only the old result used, validating migration correctness.
