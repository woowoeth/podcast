企业版把公司伪装成多个小公司

Slack早期数据按团队分片，一个客户一个库。企业版上线后，为了复用这套架构，工程团队把IBM这样的大公司内部的市场部、工程部伪装成独立的小团队，再造出一个Enterprise实体把它们粘合起来，让跨团队私信和频道能工作。结果是IBM全公司所有人查私信、查大频道时都打在同一个Enterprise分片上，这个分片很快就扛不住了。

— Maude
17:34

一次迁移差点删光全公司的Slack消息

为了合并DM、公开频道、私密频道三张分裂的表，Maude手写了一层薄薄的抽象，做双写、影子读对比数据。验证通过后她在周四的Gather Hour把开关打到全公司，结果发现数据有点不对，于是她像平时清本地环境一样直接删表重跑回填——却忘了这个开关对全Slack都生效。结果全公司的人侧边栏空白了大约半小时，期间几乎没人发现，因为大家都在Gather Hour聚会。

— Maude
28:47

CEO一句「放假」能引发表情符号雪崩

CEO在十万人频道发「大家周五放假」,这条消息通过WebSocket广播给所有人，几秒内所有人涌入频道、拉取历史、疯狂点表情庆祝。每一个表情反应也要再广播给所有人，一个表情变成十万条，十个表情就是百万条。Slack的解法不是优化架构，而是产品层面直接把一条消息上的自定义表情种类上限设成23个，多出来的直接不算。

— Maude
32:57

身兼多职的管理员每条消息收到30遍

IBM的Slack管理员Jeff同时登录在大约30个工作区里。当时架构是每个工作区各自建一条WebSocket连接，企业级的一条消息如果在这30个工作区里都共享可见，就会毫无去重地给他的客户端推送30次，导致他的客户端经常直接崩溃。这种「事件洪流」只折磨重度用户，而重度用户恰恰是Slack最忠实的拥护者。

— Maude
41:14

50万真实连接的压测，一次就花15万美元

为了验证能否扛住一个50万座席的大客户，Slack最初用Kubernetes跑海量headless Chrome实例模拟真实用户点击，但光云端算力成本就高到离谱——每个headless Chrome实例每小时3毛7分钱，一次五小时的测试就要烧掉约15万美元，而且一半时间都在重启崩溃的Pod。团队后来放弃高保真方案，改用轻量级Go进程建立真实WebSocket连接并回放录制好的API请求序列，牺牲一些保真度换取可重复、低成本的压测。

— Maude
52:46

只有16个分片撑起GitHub全部PR和Issue

GitHub用Vitess给MySQL做动态分片，但Maude加入时发现所有pull request和issue数据只分布在16个分片上，远远少于她在Slack习惯的「每个分片键配几千个分片」。原因是系统里已经存在大量「scatter查询」——没带主键、必须扫遍每个分片才能返回结果的查询——分片越多这类查询反而越慢，这形成了一个死结：想扩容必须先清理scatter查询，但清理比想象中难得多。

— Maude
57:51

五行代码，查不出一句SQL在哪里

在用ActiveRecord重写GitHub的Rails代码时，Maude和同事想揪出一个调用stars表的查询源头，结果定位到一个只有五行的函数，却完全看不到任何SQL语句的影子。她问同事「SQL在哪」,对方回答「Mo,这就是那个价值百万美元的问题」。这正是她对比Slack所用的Flamework式「SQL直接写在代码里」和GitHub ActiveRecord式「抽象到看不见SQL」两种风格后，体会最深的落差。

— Maude
59:54

GitHub页面上的计数器几乎全是实时算出来的

ActiveRecord只有在查询条件完全一致时才会命中缓存，稍微换个条件就重新查库。Maude发现GitHub一个代码库主页要跑超过100条MySQL查询、横跨至少三个MySQL集群，而且几乎所有页面上显示的计数(open PR数、issue数)都是实时计算、完全没有缓存的。她的判断是这类计数超过某个阈值后根本不需要精确——显示「99+」就够了，没必要为了一个没人在乎的数字去跑一次昂贵的实时统计。

— Maude

Event flood事件洪流
