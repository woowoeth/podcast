IDDQD 解決的是「同一個 key 存兩份」的老問題

Oxide 用 CockroachDB 存大量記錄，經常要按 UUID 之類的主鍵索引。Rust 標準 map 要求 key 和 value 分開存，於是團隊要麼把 key 複製一份存進 value（容易兩邊不同步），要麼到處傳元組（很不方便）。IDDQD 讓用戶直接存一整條記錄，由用戶定義如何從記錄裡提取 key，key 從 value 裡「借」出來而不是複製。最早的版本靠 clone 實現（仍是安全 Rust），但對不能 clone 的「自然鍵」（由幾個字段組合成的 key）不適用，於是 Rain 花了幾週找到不需要 clone、靠 unsafe Rust 實現借用的方案。

18:02

unsafe 不是關掉安全檢查，是編譯器能力的邊界

Rain 提到 Rice 定理（等價於停機問題）：不存在一個終止的算法能完美判斷任意程序是否有未定義行為。Rust 編譯器選擇「比完美更嚴格」——寧可拒絕一些實際上沒問題的程序，也要保證安全 Rust 裡絕不接受有未定義行為的程序。unsafe 就是給那些「你知道沒問題，但編譯器證明不了」的中間地帶開的逃生艙，責任轉移給了人。

— Rain Paharia
42:30

最難的 unsafe：正確性依賴於你無法信任的用戶代碼

IDDQD 的 unsafe 實現依賴用戶實現的 hash、比較等 trait，而用戶完全可以不守 Rust 規定的契約——比較函數可以隨機翻轉結果、同一個 key 兩次哈希出不同值。Rain 說這時候得用「infosec 心態」而不是「軟件工程心態」去想：攻擊者（這裡是寫壞代碼的用戶）能怎麼把你的假設打穿。關鍵原則是：用戶代碼寫錯，結果可以是跑出 bug，但絕不能讓 Rust 的底層內存安全規則被打破。

— Rain Paharia
58:40

發現 bug 的導火索是圍觀 Bun 從 Zig 重寫成 Rust

Rain 說真正促使他寫這篇博客的，是自己在 IDDQD 裡發現了一個真 bug，同時又在圍觀 Bun 項目被九天內用 AI 把一百萬行代碼從 Zig「轉譯」成 Rust、且早就停止接 PR。他認為這種轉譯本身可以接受，但代碼裡隨手寫的大量 unsafe 沒有達到他認為的「對安全 Rust 用戶負責任」的水準，這件事刺激他把「怎樣才算負責任地寫 unsafe Rust」寫清楚。

— Rain Paharia
1:05:40

可變迭代器天生違反 Rust 規則，必須靠人工承諾

Rust 1.0 前定了一個設計：迭代器返回的值可以逃出 for 循環的作用域（比如 collect 成一個 vec），這意味著你可以同時拿到 map 裡所有元素的可變引用。編譯器沒法證明這些引用彼此不重疊，所以實現 iter_mut 必須用 unsafe 手動向編譯器「保證」這些值互不相同——而如果底層 map 被用戶的錯誤代碼騙得存了重複索引，這個保證就被打破，導致兩個可變引用指向同一塊內存。

— Rain Paharia
1:11:50

修復方案：抓到用戶代碼出錯後，主動降級成低效但安全的掃描

Rain 發現可以用一個幾乎總是對、但在特定點故意返回錯誤結果的 Ord 實現，誘騙 IDDQD 存入重複索引。修復分兩步：一是用 tiebreaker 保證絕不會誤匹配到錯誤的條目；二是一旦檢測到用戶代碼已經不可信，remove 操作就從高效的索引查找降級成全程不調用用戶代碼的線性掃描——犧牲性能換取「哪怕用戶代碼壞了也絕不觸發未定義行為」的保證。

— Rain Paharia
1:24:30

用 Claude Opus 4.7 和 GPT-5.5 當對抗性測試員找到了真 bug

Rain 把自己寫的病態測試當種子，讓 LLM 去嘗試打破 map 的不變量。GPT-5.5 「嚼了大概二十分鐘」之後找到了一種真正打破不變量的方法，Claude Opus 4.7 和它各自獨立發現了一兩處。這類用法之所以好用，是因為 LLM 找到的東西可以立刻用 Miri 這類解釋器驗證，不像「vibe coding」那樣難以判斷真假。

— Rain Paharia
1:30:10

Miri 分 stacked borrows 和 tree borrows 兩套模型，IDDQD 卡在邊界上

Miri 是解釋 Rust 中間表示（MIR）的工具，用來判斷某段 unsafe 代碼是否違反別名規則。它有兩種模型：較老、被公認過嚴的 stacked borrows，和試圖放寬的 tree borrows。IDDQD 兩種都要過 CI，但 Rain 不得不為了通過 stacked borrows 專門加了一些變通寫法——說明這個庫正好踩在兩套規則分歧的邊界上。

— Rain Paharia
